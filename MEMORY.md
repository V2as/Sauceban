## Push-метрики — аддитивны

Фича сознательно не трогает старые `WEBHOOK_ADDRESS` event-уведомления.
Нет scheduler'ов в БД → джоба ничего не делает. Сбор метрик дешёвый:
агрегатный SQL + `psutil`, кэш снимка `PUSH_METRICS_CACHE_TTL` общий на все
scheduler'ы, сработавшие в один момент. Не «ускоряйте» сбор N+1 по
пользователям.

Управление в runtime через API/CLI/dashboard: reconciler каждые
`JOB_SYNC_PUSH_SCHEDULERS_INTERVAL` секунд подтягивает интервалы без
рестарта процесса. Минимум интервала — `PUSH_SCHEDULER_MIN_INTERVAL` (5 с).

Контракт для внешнего приёмника (HMAC, payload) — `USAGE-PUSH.md`, не
дублировать здесь.

## Мониторинг аномалий — откуда берутся IP

Задача: поймать подписку, которой пользуются одновременно из нескольких мест,
и «не заметить» одного человека с телефоном и ноутбуком. Блокировок нет
принципиально: фича только сообщает.

Источник данных выбран после трёх отброшенных вариантов:

- **access-log Xray.** Штатный конфиг Sauceban вообще не включает `log.access`,
  а если включить в файл — он не идёт в stdout, который мы уже читаем. Парсинг
  логов дорог и ломается о формат.
- **`GetStatsOnlineIpList` по каждому пользователю.** N gRPC-вызовов на тик.
  Оставлен только как fallback (`ANOMALY_PROBE_LIMIT` недавно активных).
- **Свой учёт коннектов.** Нужен доступ к соединениям, которого у панели нет.

Выбран `GetUsersStats(include_traffic=false)` — один вызов на ядро отдаёт всех
онлайн-пользователей с их IP. Требует `statsUserOnline` в policy (выставляется
принудительно в `app/xray/config.py`).

**Ручные protobuf-дескрипторы.** Обоих RPC нет в вендоренных стабах
`xray_api/`. Регенерировать всё дерево из свежих proto — инвазивно (конфликты
версий `protobuf`/`grpcio` и диффы в сотни файлов). Вместо этого
`xray_api/online.py` собирает минимальные дескрипторы в приватном
`descriptor_pool` в рантайме. При обновлении вендоренных стабов проверьте, не
появились ли эти сообщения там — тогда модуль можно снести.

Ядро без нужного RPC отвечает `UNIMPLEMENTED` → `NotSupportedError`, монитор
переходит на probe, потом на `ip_source: "unavailable"` с предупреждением в
отчёте. Аномалии при этом не выдумываются.

## Мониторинг аномалий — почему такие правила

Ложные срабатывания здесь дороже пропусков: обвинить платящего клиента хуже,
чем не заметить одного шарящего. Отсюда четыре ограничителя, каждый добавлен
против конкретного класса ложных тревог:

- **/24 и /64 вместо сырых IP** — сотовый оператор меняет адрес одного
  устройства посреди сессии; dual-stack клиент даёт A и AAAA одновременно.
- **`_MIN_NETWORKS_FOR_IP_RULES = 2`** — правила по количеству адресов вообще
  не стреляют, пока адреса лежат в одной сети. Добавлено после того, как
  тестовый «телефон с ротацией IP внутри одной /24» уехал в `critical`.
- **Одновременность важнее суммы за окно.** Максимальный вес — у
  `concurrent_networks` (сети в одном замере): переезжающее устройство
  посещает сети последовательно, шаринг — параллельно.
- **`min_hits` подряд** и **load gate `min_traffic_rate_mbps`**. Gate по
  умолчанию выключен (`0`): на тихой панели он бы прятал всё.

Дефолты (2 сети одновременно / 3 сети за окно / 6 IP / 2 замера) подобраны под
«продали как 1–2 устройства». Продаёте мультидевайс — поднимайте
`max_concurrent_networks`, а не выключайте правила.

Шкала severity зафиксирована в коде (35/55/75) намеренно: оператор крутит
пороги детектора, а приёмник фильтрует по severity, и она должна остаться
сравнимой между панелями.

## Мониторинг аномалий — состояние и доставка

Окно живёт **только в памяти процесса панели**: перезапуск начинает с чистого
окна, а CLI (`anomaly report`, `anomaly send-now`) видит пустое состояние —
это отдельный процесс. Настройки из CLI править можно, живую картину смотреть
— нет. В БД пишутся только настройки и вебхуки.

Находки копятся в очереди на каждый вебхук и очищаются **только после
успешной** доставки: троттлинг по `interval` или лежащий приёмник не должны
терять аномалии. Cooldown (`cooldown_seconds`) считается по пользователю и
переживает его уход в офлайн; повторный отчёт раньше срока — только если
score вырос больше чем на 15.

Доставка переиспользует `deliver()` из `send_push_metrics` (тот же HMAC и
заголовки), отличается только `User-Agent`
(`Marzban-AnomalyMonitor/1.0`) — чтобы общий приёмник различал два потока.

## xhttpSettings.extra обязан дойти до клиента

До `6c664bb` Sauceban читал `streamSettings.xhttpSettings` по фиксированному
whitelist. Поля, которые задают контракт протокола (`uplinkHTTPMethod`,
`uplinkDataPlacement`, `sessionID*`, `seq*`, `xPadding*` и т.п.), живут только
в `extra`. Сервер с GET-upload раздавал ссылки, по которым клиент не
коннектился.

Сейчас `extra` уходит: как плоский query-param `extra` в vless/vmess/trojan
ссылках и как вложенный `xhttpSettings.extra` в JSON-подписке. Значения
inbound побеждают дефолты Sauceban. Inbound без `extra` не меняется.
Точки: `app/subscription/v2ray.py`, `app/xray/config.py`.

## Один процесс — один scheduler и один Xray

Multi-worker uvicorn сознательно запрещён (`main.py`): APScheduler и модуль
Xray не шарят состояние между воркерами. Масштабирование — ноды Marzban
(`app/xray/node.py`), не `--workers`.

## Схема БД

Миграции только через Alembic (`alembic.ini` → `app/db/migrations`).
`SQLALCHEMY_DATABASE_URL` может указывать на SQLite / MySQL / Postgres —
не пишите диалект-специфичный SQL в CRUD без проверки всех трёх. Миграция
push (`f1a2b3c4d5e6`) идемпотентна: если таблица уже есть, `upgrade`
выходит сразу (нужно было для уже раскатанных панелей).

## Дашборд

`app/dashboard/build` коммитится, `node_modules` — нет. CI `build.yml`
собирает dashboard на Node 20 перед образом; локально повторяйте команду CI
целиком, включая флаги и `404.html`:

```bash
cd app/dashboard && npm ci
VITE_BASE_API=/api/ npm run build -- --outDir build --assetsDir statics
cp build/index.html build/404.html
```

Голый `npm run build` кладёт результат в `dist/assets` — панель его не
раздаёт, а закоммиченный `build/` останется от прошлой сборки.

## CI vs рабочая ветка

`main` — рабочая. Публикация образа: push в **`master`** или тег `v*.*.*`.
Не обещайте «запушил в main — уехало на Hub».
