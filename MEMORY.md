## Форк, не апстрим

Sauceban = Marzban + локальные аддоны. README*/CONTRIBUTING/LICENSE — от
Gozargah/Marzban. Не правьте их «под Sauce», пока это не осознанный rebase

## Push-метрики — аддитивны

Фича сознательно не трогает старые `WEBHOOK_ADDRESS` event-уведомления.
Нет scheduler'ов в БД → джоба ничего не делает. Сбор метрик дешёвый:
агрегатный SQL + `psutil`, кэш снимка `PUSH_METRICS_CACHE_TTL` общий на все
scheduler'ы, сработавшие в один момент. Не «ускоряйте» сбор N+1 по
пользователям.

Управление в runtime через API/CLI/dashboard: reconciler каждые
`JOB_SYNC_PUSH_SCHEDULERS_INTERVAL` секунд подтягивает интервалы без
рестарта процесса. Минимум интервала — `PUSH_SCHEDULER_MIN_INTERVAL` (5 с).

Контракт для внешнего приёмника (HMAC, payload) — `USAGE-PUSH.md`, не
дублировать здесь.

## Мониторинг аномалий — откуда берутся IP

Задача: поймать подписку, которой пользуются одновременно из нескольких мест,
и «не заметить» одного человека с телефоном и ноутбуком. Блокировок нет
принципиально: фича только сообщает.

Источник данных выбран после трёх отброшенных вариантов:

- **access-log Xray.** Штатный конфиг Sauceban вообще не включает `log.access`,
  а если включить в файл — он не идёт в stdout, который мы уже читаем. Парсинг
  логов дорог и ломается о формат.
- **`GetStatsOnlineIpList` по каждому пользователю.** N gRPC-вызовов на тик.
  Оставлен только как fallback (`ANOMALY_PROBE_LIMIT` недавно активных).
- **Свой учёт коннектов.** Нужен доступ к соединениям, которого у панели нет.

Выбран `GetUsersStats(include_traffic=false)` — один вызов на ядро отдаёт всех
онлайн-пользователей с их IP. Требует `statsUserOnline` в policy (выставляется
принудительно в `app/xray/config.py`).

**Три RPC — три версии ядра.** Upstream добавлял их по частям, поэтому в
`_collect` лестница фолбэков, а не один вызов:

| Xray-core | RPC |
|---|---|
| ≥ `v25.2.18` | `GetStatsOnlineIpList` (IP одного пользователя) |
| ≥ `v25.12.1` | `GetAllOnlineUsers` (кто сейчас онлайн) |
| ≥ `v26.4.13` | `GetUsersStats` (всё за один вызов) |

Версии из истории `app/stats/command/command.proto`; по коду их не
восстановить. Ядро старше `v25.2.18` — детектор бесполезен, это не баг
панели, и предупреждение в отчёте говорит об этом прямым текстом.

`GetAllOnlineUsers` добавлен в цепочку после бага: без него список кандидатов
для probe строился из `users.online_at`, который обновляет `record_usages` по
факту трафика. Подключённый, но простаивающий пользователь в список не
попадал, и на тихой панели детектор навсегда оставался в `unavailable`, хотя
ядро всё умело.

**Ручные protobuf-дескрипторы.** Обоих RPC нет в вендоренных стабах
`xray_api/`. Регенерировать всё дерево из свежих proto — инвазивно (конфликты
версий `protobuf`/`grpcio` и диффы в сотни файлов). Вместо этого
`xray_api/online.py` собирает минимальные дескрипторы в приватном
`descriptor_pool` в рантайме. При обновлении вендоренных стабов проверьте, не
появились ли эти сообщения там — тогда модуль можно снести.

Ядро без нужного RPC отвечает `UNIMPLEMENTED` → `NotSupportedError`, монитор
переходит на probe, потом на `ip_source: "unavailable"` с предупреждением в
отчёте. Аномалии при этом не выдумываются.

## Мониторинг аномалий — почему такие правила

Ложные срабатывания здесь дороже пропусков: обвинить платящего клиента хуже,
чем не заметить одного шарящего. Отсюда четыре ограничителя, каждый добавлен
против конкретного класса ложных тревог:

- **/24 и /64 вместо сырых IP** — сотовый оператор меняет адрес одного
  устройства посреди сессии; dual-stack клиент даёт A и AAAA одновременно.
- **`_MIN_NETWORKS_FOR_IP_RULES = 2`** — правила по количеству адресов вообще
  не стреляют, пока адреса лежат в одной сети. Добавлено после того, как
  тестовый «телефон с ротацией IP внутри одной /24» уехал в `critical`.
- **Одновременность важнее суммы за окно.** Максимальный вес — у
  `concurrent_networks` (сети в одном замере): переезжающее устройство
  посещает сети последовательно, шаринг — параллельно.
- **`min_hits` подряд** и **load gate `min_traffic_rate_mbps`**. Gate по
  умолчанию выключен (`0`): на тихой панели он бы прятал всё.

Дефолты (2 сети одновременно / 3 сети за окно / 6 IP / 2 замера) подобраны под
«продали как 1–2 устройства». Продаёте мультидевайс — поднимайте
`max_concurrent_networks`, а не выключайте правила.

Шкала severity зафиксирована в коде (35/55/75) намеренно: оператор крутит
пороги детектора, а приёмник фильтрует по severity, и она должна остаться
сравнимой между панелями.

## Мониторинг аномалий — состояние и доставка

Окно живёт **только в памяти процесса панели**: перезапуск начинает с чистого
окна, а CLI (`anomaly report`, `anomaly send-now`) видит пустое состояние —
это отдельный процесс. Настройки из CLI править можно, живую картину смотреть
— нет. В БД пишутся только настройки и вебхуки.

Находки копятся в очереди на каждый вебхук и очищаются **только после
успешной** доставки: троттлинг по `interval` или лежащий приёмник не должны
терять аномалии. Cooldown (`cooldown_seconds`) считается по пользователю и
переживает его уход в офлайн; повторный отчёт раньше срока — только если
score вырос больше чем на 15.

Доставка переиспользует `deliver()` из `send_push_metrics` (тот же HMAC и
заголовки), отличается только `User-Agent`
(`Marzban-AnomalyMonitor/1.0`) — чтобы общий приёмник различал два потока.

## Чёрный список — почему лимит режется ядром

Задача: ограничить выбранному пользователю канал до N Мбит/с, не ломая
обновление уже раскатанных панелей. Отброшенные варианты:

- **Правила маршрутизации Xray.** Per-user rate limit ядро не умеет вообще;
  `sockopt.mark` только метит пакеты — резать всё равно нужно ядром ОС, а
  конфиг при этом пришлось бы перегенерировать на каждое изменение лимита.
- **Опрос счётчиков и кик пользователя.** Реакция на порядок медленнее, режет
  не скорость, а сессию; «превысил — отключили» это не то, что просили.
- **Отдельный прокси/шейпер перед Xray.** Лишний хоп в продовом трафике.

Выбран `tc`: HTB-классы на egress (download) и policer на ingress (upload)
по адресам, которые ядро Xray отдаёт в online-IP stats. Тот же источник, что
у детектора аномалий, — новых зависимостей и опросов не появилось.

**Ingress полисится, а не шейпится** — очередь на входе потребовала бы
устройство `ifb` и его модуль; отбрасывание сверхлимитных пакетов TCP
отрабатывает сам. **Лимит на направление**, а не общий: так проще объяснить
оператору и не нужно делить полосу между up/down.

**Нужен `NET_ADMIN`** у контейнера (`docker-compose.yml`, шаблоны и
`ensure_net_admin_cap` в `sauceme.sh`) и `iproute2` в образе. Без прав фича
не падает: записи остаются, API работает, `status.unavailable_reason`
объясняет, что чинить. Проверка живёт в `up_marzban`, а не в `update`:
`update` сначала подменяет сам скрипт, поэтому панель, обновляющаяся со
старой версии, иначе получала бы capability только со второго обновления —
на боевой панели это закончилось тем, что лимит месяцами сохранялся в БД и
никогда не доезжал до ядра.

**Чужой root qdisc не трогаем.** Если на интерфейсе уже висит не-дефолтный
шейпер, фича отказывается работать и говорит об этом: молча снести чужие
правила хуже, чем не ограничить.

**Только хост панели.** Трафик пользователя, подключённого через удалённую
ноду, через этот хост не идёт — резать там нечего, нужен агент на ноде.

TTL адреса (`BLACKLIST_IP_TTL`, 180с) — чтобы клиент, замолчавший между
семплами, не терял и не получал заново правила. Один адрес на двух
ограниченных пользователей достаётся более строгому лимиту.

## Лимит всем сразу — состояние держит ядро, а не панель

Задача: «по 200 Мбит каждому», а не 200 Мбит на всех, и чтобы это было дешёво
по CPU и RAM. Отброшенные варианты:

- **Растянуть механизм чёрного списка на всех.** Класс `tc` на каждого
  онлайн-пользователя плюс опрос online-IP ради самого списка адресов: цена
  тика растёт с числом онлайн, цепочка фильтров переписывается на каждый
  вход-выход клиента, реакция — до `JOB_SYNC_BLACKLIST_INTERVAL`.
- **Хеш-бакеты в `tc`** (u32-хеш по адресу, класс на бакет). Дёшево и без
  новых зависимостей, download шейпился бы очередью, но у u32 максимум 256
  бакетов на уровень: при сотне онлайн-адресов часть пар делит один лимит.
  «Двум случайным клиентам иногда достаётся по 100 Мбит вместо 200» — это то,
  что оператор не сможет объяснить, и хуже, чем полисинг вместо шейпинга.
- **`cake` с `dual-dsthost`.** Даёт честное деление канала между хостами, а
  просили фиксированный лимит каждому; на ingress всё равно нужен `ifb`.

Выбран `nft`: динамический сет с `limit rate over` на элемент — по два правила
на направление, бакет на адрес создаёт **ядро** при первом пакете и забывает
через `GLOBAL_LIMIT_IP_TIMEOUT`. Панель при этом не знает и не спрашивает, кто
онлайн: тик стоит SELECT и сравнение кортежа, `nft` вызывается только на
изменение настройки. Полисинг в обе стороны (а не очередь) — сознательная цена
за это: очередь на download требует очереди на каждый адрес, то есть ровно
того, чего избегаем.

**Единица — адрес, не аккаунт.** Пользователь с двумя устройствами получит
лимит дважды, устройства за одним NAT поделят один. Считать «на аккаунт»
означало бы снова знать, чьи это адреса, — см. первый отброшенный вариант.

**`ct direction` обязателен: без него лимит становится общим на всех.** На
внешнем интерфейсе «дальний конец» пакета — это клиент только для соединений,
которые открыл клиент; для того, что панель сама тянет из интернета, дальний
конец — сайт. Правило без проверки направления заводило бакет на адрес сайта,
и все, кто качал с одного хоста, делили один лимит. На панели с цепочкой на
апстрим это вырождается в «один бакет на всю панель»: обратный трафик всех
клиентов приходит с одного адреса релея — именно так лимит 10 Мбит/с
превращался в 1–2 Мбит/с на человека. Клиент — та сторона, что открыла
соединение: на входе это `original`, на выходе `reply`.

**Два лимита складываются, а не заменяют друг друга.** Никакого списка
исключений: пользователь из чёрного списка режется и `tc`, и `nft`, побеждает
более строгий. Исключения потребовали бы синхронизировать сет адресов с
онлайн-состоянием — цена той самой лёгкости, ради которой всё это выбрано.

**Своя таблица `sauceban_bandwidth`, целиком заменяемая транзакцией.**
`nft -f` с `table {}` + `delete table` + определением идемпотентен и атомарен:
отказ (нет `NET_ADMIN`) ничего не меняет, поэтому после ошибки состояние в
памяти всё ещё верно описывает ядро. Раз в минуту — проверка, что таблица на
месте: чужой `nft flush ruleset` унёс бы её молча.

**Настройка в БД (`bandwidth_settings`), а не в env.** Переключатель живёт в
дашборде — значит должен переживать рестарт без редеплоя. `BLACKLIST_ENFORCE`
остаётся общим выключателем «применять ли лимиты в ядре вообще».

**`burst` у лимита не задаём.** У байтового `limit` бакет по умолчанию уже
равен секунде трафика — этого хватает и на джиттер туннеля, и на 64K-пакеты
от segmentation offload, а меньше сделать всё равно нельзя.

## Авто-замедление нарушителя — чья запись главнее

Детектор аномалий умеет сам вешать лимит на нарушителя. Своего механизма
ограничения у него нет и не будет: он пишет строку в `blacklist_users` с
`source='anomaly'` и `expires_at`. Заводить вторую таблицу и второй шейпер
значило бы решать конфликт двух ограничений в ядре; так конфликт решается
одной строкой на пользователя.

**Оператор главнее автоматики.** На ручной записи автоматика не делает
ничего (`kept_manual` в отчёте), а любое сохранение авто-записи через API
или UI переводит её в `manual` и снимает срок. Обратного перехода нет:
молча вернуть себе запись, которую правил человек, — худший из возможных
сюрпризов.

**Повторная аномалия продлевает, но не ужесточает.** Каждый замер, где
пользователь всё ещё аномален, двигает `expires_at` на
`now + throttle_seconds`, то есть отсчёт начинается с момента, когда шаринг
прекратился. Подавленные cooldown'ом находки тоже продлевают: это та же
продолжающаяся аномалия, и наказание не должно сниматься из-за того, что о
ней перестали рассказывать в вебхук.

**Срок снимает джоба чёрного списка, а не детектор.** Иначе выключение
мониторинга (или его падение) оставляло бы вечные лимиты, а включение
возвращало бы полосу пачкой. Побочно это значит, что лимит истекает с
точностью до `JOB_SYNC_BLACKLIST_INTERVAL`.

**Порог замедления отдельный от `min_severity` вебхуков.** Рассказать о
находке и наказать за неё — разные решения: обычно хочется знать про
`medium`, а резать только `high`. Дефолт — `high`, выключено.

Отдельных событий «замедлил / снял» в вебхук нет: приёмник получает блок
`throttle` внутри той же находки. Отдельный поток событий потребовал бы
своей очереди и гарантий доставки ради информации, которая и так есть в
`/api/blacklist`.

## Счётчики online отдают имя счётчика, а не email

`GetAllOnlineUsers`/`GetUsersStats` возвращают `user>>>EMAIL>>>online` —
имя stat-счётчика, а не email. Сравнение с `f"{id}.{username}"` не совпадало
никогда: детектор аномалий на ядрах с bulk-RPC молча не видел никого.
Нормализация теперь в `xray_api/stats.py` (одна точка на обе фичи), а не в
джобах.

## xhttpSettings.extra обязан дойти до клиента

До `6c664bb` Sauceban читал `streamSettings.xhttpSettings` по фиксированному
whitelist. Поля, которые задают контракт протокола (`uplinkHTTPMethod`,
`uplinkDataPlacement`, `sessionID*`, `seq*`, `xPadding*` и т.п.), живут только
в `extra`. Сервер с GET-upload раздавал ссылки, по которым клиент не
коннектился.

Сейчас `extra` уходит: как плоский query-param `extra` в vless/vmess/trojan
ссылках и как вложенный `xhttpSettings.extra` в JSON-подписке. Значения
inbound побеждают дефолты Sauceban. Inbound без `extra` не меняется.
Точки: `app/subscription/v2ray.py`, `app/xray/config.py`.

## Джоба статусов не имеет права читать всех пользователей

На панели с 20k аккаунтов (17.9k активных, 450 онлайн) «Сохранить» в
дашборде висел по полминуты, хотя сам эндпоинт отвечает за 15 мс.
Виновата оказалась `review_users`: каждые `JOB_REVIEW_USERS_INTERVAL`
(10 с по умолчанию) она делала `get_users(status=active)` — выборку всех
активных с `joinedload` админа и next-plan. В slow-log такой запрос занимал
до 37 секунд, отдавал 2 МБ строк и разворачивался в сотни мегабайт ORM-объектов;
каждый тик клал MariaDB и выбивал память, из-за чего OOM-killer убивал xray
(26 раз за день), панель пересобирала конфиг ядра на 18k пользователей — и
всё повторялось. Чтение из буферного пула при этом продолжало отвечать
быстро, поэтому UI выглядел живым, а висели именно записи: COMMIT ждал
перегруженный InnoDB.

Поэтому условия джобы переехали в SQL (`crud.get_users_to_review`,
`get_on_hold_users_to_review`): БД отдаёт только тех, у кого кончился трафик
или срок, плюс — если включены вебхуки — подошедших к порогам напоминаний
(порог берётся минимальный/максимальный, окно по дням расширено на сутки,
потому что `calculate_expiration_days` округляет вниз). На той же боевой базе
это 26 мс и ноль строк вместо 37 секунд и 17 973 строк.

Общее правило: периодическая джоба не должна тянуть таблицу пользователей
целиком. Нужен обход всех — делайте его пакетами и не чаще, чем реально
нужно.

## Один процесс — один scheduler и один Xray

Multi-worker uvicorn сознательно запрещён (`main.py`): APScheduler и модуль
Xray не шарят состояние между воркерами. Масштабирование — ноды Marzban
(`app/xray/node.py`), не `--workers`.

## Схема БД

Миграции только через Alembic (`alembic.ini` → `app/db/migrations`).
`SQLALCHEMY_DATABASE_URL` может указывать на SQLite / MySQL / Postgres —
не пишите диалект-специфичный SQL в CRUD без проверки всех трёх. Миграция
push (`f1a2b3c4d5e6`) идемпотентна: если таблица уже есть, `upgrade`
выходит сразу (нужно было для уже раскатанных панелей). Так же сделаны
миграции аномалий (`b7c8d9e0f1a2`), чёрного списка (`c3d4e5f6a7b8`) и
авто-замедления (`d4e5f6a7b8c9` — проверяет каждую колонку перед `ADD`).

Аддоны Sauce кладут данные в **свои таблицы**, а не расширяют `users`:
обновление панели не должно упираться в ALTER большой боевой таблицы.

## Дашборд

`app/dashboard/build` коммитится, `node_modules` — нет. CI `build.yml`
собирает dashboard на Node 20 перед образом; локально повторяйте команду CI
целиком, включая флаги и `404.html`:

```bash
cd app/dashboard && npm ci
VITE_BASE_API=/api/ npm run build -- --outDir build --assetsDir statics
cp build/index.html build/404.html
```

Голый `npm run build` кладёт результат в `dist/assets` — панель его не
раздаёт, а закоммиченный `build/` останется от прошлой сборки.

## CI vs рабочая ветка

`main` — рабочая. Публикация образа: push в **`master`** или тег `v*.*.*`.
Не обещайте «запушил в main — уехало на Hub».
